🌴 Aurelia Resort Management System – High Level Design

Scope: guest booking (web + PWA app) and admin management. Demo build is a modular monolith; production upgrades are listed as future phase.

Dashed boxes = future phase, not built in demo.

2. Database (ER)

TableColumns
roomid PK, name, type, capacity, price, image
bookingid PK, room_id FK→room, guest_name, email, phone, check_in, check_out, total, status (CONFIRMED / CANCELLED)
users (future)id PK, name, email, password_hash, role (GUEST / ADMIN)
payment (future)id PK, booking_id FK, gateway_ref, amount, status

Relation: one room has many bookings. Availability rule: a booking overlaps if check_in < new.check_out AND check_out > new.check_in and status is not CANCELLED.

4. Booking flow

  1. Guest picks dates → API returns only free rooms
  2. Guest selects room, enters details
  3. Server revalidates dates and availability, calculates total = price × nights
  4. Mock payment succeeds → booking saved as CONFIRMED
  5. Admin sees booking and revenue on dashboard

5. Tech choices and why

  • Spring Boot modular monolith: fastest to build and deploy; modules can split into microservices later
  • React + PWA: one codebase serves web and installable app
  • Basic auth in demo: JWT with Spring Security planned for production
  • Docker on Render, Vercel for frontend: free HTTPS deployment

6. Scalability design

LayerStrategy
APIStateless (JWT, no server session), so N instances run behind a load balancer; Kubernetes HPA autoscaling on CPU / request rate
DatabaseManaged PostgreSQL / MySQL, indexes on room_id, check_in, check_out; read replicas for search; connection pooling
CacheRedis for room list and availability search results, short TTL
Static / imagesFrontend and images on CDN, so API does not serve them
Async workKafka / RabbitMQ queue for email, SMS, payment webhooks; booking API stays fast
ProtectionRate limiting at gateway, health checks, timeouts, circuit breakers
ObservabilityPrometheus + Grafana metrics, centralised logs, alerts

Honest note: the demo runs on one small instance. The design allows horizontal scaling; real capacity numbers need a load test (k6 / JMeter).

7. Concurrency control and dynamic pricing

Double booking prevention: booking runs in one transaction. The room row is locked (pessimistic write lock) first, then availability is checked, then the booking is saved. Two guests booking the same room and dates at the same moment: the second waits, then gets a conflict. At larger scale: add a DB constraint or Redis distributed lock.

Dynamic pricing (per night): weekend (Fri, Sat) +20%, peak season Oct to Feb +15%, last-minute (within 3 days) +10%. Server calculates the quote and the final total, so the client cannot tamper with prices.

AI concierge: floating chat in web and PWA. The browser calls our backend, and the backend calls the Claude API with a system prompt built from live room data and pricing rules. The API key stays in a server environment variable, never in the frontend. Protections: 15 messages per minute per IP, message length and history limits, spend limit on the API account. Guests can ask in English, Hindi or Marathi. Without an API key the concierge falls back to a rule-based demo mode (budget, family, pricing questions answered from live room data), clearly labelled in the chat; connecting a key switches it to full AI.
